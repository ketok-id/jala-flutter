# jala_grpc

**gRPC** adapter for Jala (`package:grpc`): a `ClientInterceptor` that
captures unary and streaming RPCs — service/method, messages, metadata,
status codes and trailers.

> [What is Jala?](../../README.md) · [Package map](../../docs/packages.md) ·
> [Doc index](../../docs/README.md)

| | |
|---|---|
| **Audience** | Apps using `package:grpc` (gRPC or gRPC-web) |
| **Depends on** | `jala_core`, `grpc` |
| **Lockstep** | `0.8.x` — [COMPAT.md](../../docs/COMPAT.md) |
| **Requires** | Dart `^3.11` |

Wire the facade with [`jala`](../jala). Brownfield:
[ADOPTION.md](../../docs/ADOPTION.md).

**Note:** this adapter is **capture only** — gRPC calls are never mocked,
delayed, or dropped by Jala. See [Limitations](#limitations).

---

## Install

```yaml
dependencies:
  jala: ^0.8.0
  jala_grpc: ^0.8.0
```

## Setup

Pass the interceptor to your generated client:

```dart
import 'package:grpc/grpc.dart';
import 'package:jala_grpc/jala_grpc.dart';

final endpoint = Uri.parse('grpc://api.example.com');
final channel = ClientChannel('api.example.com');

final client = RouteGuideClient(
  channel,
  interceptors: <ClientInterceptor>[
    JalaGrpcInterceptor(endpoint: endpoint),
  ],
);
```

### Why pass `endpoint`?

A `ClientInterceptor` is never told which channel it runs on — that is
private to the `Client`. Omit `endpoint` and entries show placeholder
`grpc://unknown-endpoint`; everything else still captures.

### Generated stubs must be recent

Interceptors only run through `$createUnaryCall` / `$createStreamingCall`.
Stubs generated by `protoc_plugin` older than 19.2.0 call the deprecated
`$createCall`, which **bypasses interceptors entirely** — regenerate them if
nothing shows up in the inspector.

## What is captured

| | request message | response message(s) | status / trailers |
|---|---|---|---|
| unary | ✅ | ✅ | ✅ |
| streaming | sent bytes only | ❌ | ✅ |

Messages are captured as proto3 JSON where the generated type provides
`toProto3Json()`, and as size-only metadata otherwise. Redaction applies to
them exactly as it does to any other JSON body —
[CONFIG.md](../../docs/CONFIG.md).

## Limitations

Both follow from `ClientInterceptor` being a narrower extension point than
the HTTP adapters' interceptor/wrapper hooks. Verified against `grpc 5.1.0`;
see [the Track G plan](../../docs/plans/track-g-v0.8-grpc.md) for the
source-level detail and the escape routes under consideration.

- **Streaming response messages are not captured.** `ResponseStream` is a
  single-subscription stream whose only constructor takes a `ClientCall`
  private to the call site, so Jala can neither tap it (that would steal
  your app's subscription) nor rebuild an equivalent one. A streaming RPC
  records its envelope, not its payloads.
- **Mocking and throttling do not apply.** Both need to fabricate or delay a
  response, which means constructing a `ResponseFuture` / `ResponseStream`.
  `JalaMockRegistry` and `JalaThrottleRegistry` are not consulted here, and
  an active throttle profile leaves gRPC traffic untouched.

## Production safety

- No-op when `!isEnabled` — both hooks forward straight to the invoker
- Capture in `try`/`catch`; the invoker's own response object is always
  returned unchanged, preserving `cancel()`, `headers` and `trailers`
- Redaction + body caps via `JalaConfig` — [CONFIG.md](../../docs/CONFIG.md)
